# AGENTS.md

Operating manual for agents and contributors working on this repository.

## Layout

| Path | Kind | Edit by hand? |
|---|---|---|
| `skills/swift-evolution/SKILL.md` | hand-written | yes (maintainer writes the prose) |
| `skills/swift-evolution/references/toolchain-detection.md` | hand-written | yes |
| `skills/swift-evolution/references/*` (everything else) | generated by `scripts/sync.mjs` | **never** |
| `scripts/` | sync, validator, snippet extractor | yes |
| `tests/scenarios/` | test packages and expected behaviour | yes |

Generated files start with `> Generated by scripts/sync.mjs`. Hand-written files under `references/` are listed in `HANDWRITTEN` in `scripts/sync.mjs`; add new ones there first, or sync will refuse to touch the path.

## Checks before every commit

```bash
node scripts/sync.mjs --check
node scripts/validate.mjs
node scripts/validate.test.mjs
```

CI runs the same checks and type-checks every ```swift block in the hand-written files with the `swift:6.4` image. Put `<!-- no-compile -->` on the line before a block that is a fragment or needs Apple SDKs.

## Citing proposals in hand-written files

Every SE number needs an annotation the validator can check:

- shipped: `SE-0481 (6.3)` or `SE-0481 (Swift 6.3)`
- not in any release: `SE-0510 (unreleased)`
- in a table row with a single SE number, a cell holding just the version counts as the annotation

Never write a version from memory. Look it up in `references/versions/`.

## Commits

- Generated changes go in their own commit, separate from hand-written changes.
- Every commit is authored by the maintainer (`zghanw`). No `Co-Authored-By` or other attribution trailers.
- Merge the weekly `sync/<commit>` pull requests with **Rebase and merge** so commit authorship is kept.

## Release-day checklist

When a new `swift-X.Y-RELEASE` tag appears (`release-watch.yml` opens an issue):

1. Run the `sync` workflow (or `node scripts/sync.mjs`) and merge its PR.
2. Run `node scripts/validate.mjs`; fix any hand-written citation it flags, including the expected behaviour in `tests/scenarios/README.md`.
3. Bump the Swift image in `.github/workflows/check.yml`.
4. Update the version mentioned in `README.md` and the `description` in `SKILL.md`.
5. Tag a repo release and write the changelog.
6. Draft the announcement.
